Guidance for Claude Code (claude.ai/code) when working in this repository.

## Project docs — read these first

`docs/` holds the living context for this project. Skim the relevant ones
before starting work; they are the source of truth, not this file.

| File | What it covers |
|---|---|
| `docs/PLANNING.md` | What TCS ERP is, the phase plan, what's in scope vs deferred. |
| `docs/STACK.md` | Tech choices (frontend, backend, tooling, hosting) and open questions. |
| `docs/CONSTRAINTS.md` | Non-negotiables and limitations — data safety, statutory accuracy, solo-dev workflow, the eventual TCS OS merge. |
| `docs/DESIGN.md` | Backend/architectural conventions the schema and RLS actively depend on. |
| `docs/JOURNAL.md` | Running dated log of decisions and milestones, newest at the bottom. |

**Keeping the docs current is part of finishing a task, not a separate
chore.** When a session produces a real decision — a scope change, a newly
discovered constraint, a tech choice resolved, a new design convention —
update the relevant doc in the same session, and always append a short
dated entry to `docs/JOURNAL.md` regardless. Show the doc diff alongside
the code changes so it can be reviewed. Don't wait to be asked.

## Repo layout

Two independent parts at the root:

- `frontend/` — the app (TanStack Start + React + TypeScript). All app
  commands run from here.
- `supabase/` — the Supabase CLI project. `supabase/migrations/` is the
  entire schema, applied in order; `supabase/seed.sql` seeds local dev;
  `supabase/functions/` holds Edge Functions. The root `package.json`
  exists only to hold the `supabase` CLI as a dev dependency.

## Commands

From `frontend/`:

```sh
npm i               # install
npm run dev         # dev server (Vite, port 8080)
npm run build       # production build
npm run build:dev   # build in development mode
npm run preview     # preview a production build
npm run lint        # eslint .
npm run format      # prettier --write .
```

Package manager: **npm** (`frontend/package-lock.json`). Don't use bun —
its stale lockfile was removed. See `docs/STACK.md`.

From the repo root, for the local Supabase stack:

```sh
npx supabase start
npx supabase stop
npx supabase db reset          # re-apply migrations + seed
npx supabase gen types typescript --local > frontend/src/lib/database.types.ts
```

Regenerate `database.types.ts` after any schema change rather than
hand-editing it.

There is no test suite/framework in this repo (no test script, no test
files).

## Routing (TanStack Start)

File-based routing under `frontend/src/routes/` — see
`frontend/src/routes/README.md` for the full convention table. Key points:

- Every `.tsx` directly under `routes/` is a route. There is no
  `src/pages/` or `app/` convention here.
- Dotted filenames express nesting/dynamic segments, e.g.
  `customers.$customerId.tsx` → `/customers/:customerId`,
  `inventory.index.tsx` → `/inventory`,
  `sales.$invoiceId.edit.tsx` → `/sales/:invoiceId/edit`.
- `routes/__root.tsx` is the single app shell (wraps every page via
  `AppShell`, provides `QueryClientProvider`, `ThemeProvider`, the
  404/error boundary, and the `<Outlet />` all other routes render into).
  Don't remove the `<Outlet />`.
- `src/routeTree.gen.ts` is auto-generated by the router plugin — never
  hand-edit it.

## Backend / data layer

Schema lives entirely in `supabase/migrations/`, applied in order. All
financial calculation happens in `plpgsql` functions in the database — the
client calls a function and displays the result, it never computes a
total or a tax figure itself.

**Conventions the schema and RLS depend on are documented in
`docs/DESIGN.md`** — create-can't-overwrite RPCs, `drop function` before
changing an argument list, explicit per-table grants, the three-tier
RLS role model, server-forced identity columns, computed-never-stored,
nullable-override-with-global-default, no-update-after-posted, the
`getErrorMessage()` duck-typing quirk, and the TCS-specific
effective-dated-config and flexible-allowance patterns. Read that file
before adding a table or an RPC; update it if you introduce or change a
convention.

Operational specifics not covered there:

- **Settings is `localStorage`-only.** `frontend/src/data/settings-store.ts`
  persists to `localStorage` (key `tcs.document-settings`) via
  `persist()`/`hydrate()`. It is not Supabase-backed and there is no sync;
  it survives a reload in the same browser and nothing else. A few narrow
  values that a database function needs a trustworthy source for
  (e.g. VAT rate, expense categories) live in real tables instead — the
  rest of Settings stays local.
- **`frontend/src/lib/supabase.ts` has an SSR-only `ws` transport guard.**
  `supabase-js` always constructs a realtime client even when nothing
  opens a channel, and that constructor throws on Node < 22 (no native
  `WebSocket`) unless a transport is supplied. The guard
  (`import.meta.env.SSR && typeof WebSocket === "undefined"`) keeps `ws`
  out of the browser bundle and SSR working. Keep it if touching this file.
- **`supabase/config.toml` does not auto-expose new tables**
  (`api.auto_expose_new_tables` is off), so a new table 403s via the Data
  API until it has explicit grants — see the grants convention in
  `docs/DESIGN.md`.
- **Before committing anything under `supabase/migrations/`**, run
  `scripts/check-duplicate-function-overloads.sh` alongside lint and
  `npx supabase db reset`.

## Local dev-only test accounts

Three throwaway staff accounts, one per role, for signing in at `/login`
while developing locally. They are **not** created by any migration or by
`seed.sql` (so a plaintext password never lands in a file a `db push`
could send to a real project). Create/recreate them with:

```sh
./scripts/seed-local-dev-staff.sh
```

It talks only to the local Supabase Auth Admin API (refuses to run if
`supabase status`'s `API_URL` isn't `127.0.0.1`/`localhost`) and is safe
to re-run after every `supabase db reset`.

| Email | Password | Role |
|---|---|---|
| `dev-attendant@tcs.test` | `local-dev-2026` | Attendant |
| `dev-manager@tcs.test` | `local-dev-2026` | Manager |
| `dev-auditor@tcs.test` | `local-dev-2026` | Accountant/Auditor |

Separately, `supabase/seed.sql` still contains historical dummy staff
accounts (`*.@tcs.internal`, shared password `password123`) that exist
only to give seeded historical records an attributable author — not for
logging in and clicking around. That seed data is still Wilelik's retail
dummy data pending replacement; see `docs/CONSTRAINTS.md`. Don't add a
credentialed account to `seed.sql`; use the script above.

## Bootstrapping the first production Manager

Public signup is disabled at the GoTrue level. The only way a staff login
is created is an invite (`supabase.auth.admin.inviteUserByEmail()`), sent
from Settings → Staff by an existing active Manager. On a brand new hosted
project nobody exists to send that first invite, so run once, by hand,
with the real project's `service_role` key:

```sh
SUPABASE_URL="https://<project-ref>.supabase.co" \
SUPABASE_SERVICE_ROLE_KEY="<the real project's service_role key>" \
MANAGER_EMAIL="owner@example.com" \
MANAGER_NAME="Real Owner Name" \
./scripts/bootstrap-production-manager.sh
```

It sends a real invite (role `Manager`) and then flips `staff.protected =
true` on the resulting row, after which a trigger makes that row's role,
active status, and protected flag unchangeable and the row undeletable for
every role including Manager. Requires typing `BOOTSTRAP` at the prompt;
refuses to run against a `127.0.0.1`/`localhost` URL. The hosted project's
own Dashboard signup toggle (Authentication → Sign In / Providers) must
also be off — `config.toml`'s `enable_signup = false` only controls local
dev. **Never run this script for the user** — it's their own step, with
their own credentials, against their own project.

  (`components.json`: style `new-york`, Tailwind CSS variables, Lucide
  icons, aliases `@/components`, `@/lib`, `@/hooks`, `@/ui`). Add new

  `settings/`, `print/`, `import/`, `layout/`).

  `lib/pdf/invoice-pdf.ts` (PDF generation via jsPDF).
- Real TCS logo/icon assets are still pending — the sidebar and login
  render a plain text "TCS" badge as a placeholder (see `docs/JOURNAL.md`).

## SSR error handling

`frontend/src/server.ts` wraps the TanStack Start server entry to catch
two failure modes: uncaught throws, and h3 swallowing in-handler errors
into a generic 500 JSON body. Both are normalized into an HTML error page
via `lib/error-page.ts`, with the real error recovered from
`lib/error-capture.ts` (`consumeLastCapturedError`) where possible.
`vite.config.ts` points the server entry at this file — don't remove that
redirect or SSR errors go back to being swallowed.

## Linting / formatting

- `@typescript-eslint/no-unused-vars` is off in `eslint.config.js`.
- Prettier: 100 print width, double quotes, semicolons, trailing commas
  everywhere (`.prettierrc`).
- `no-restricted-imports` blocks the `server-only` package — this is
  TanStack Start, not Next.js; use a `*.server.ts` filename or
  `@tanstack/react-start/server-only`.

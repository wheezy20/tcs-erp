# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repo layout

This repo has two independent parts at the root:

- `frontend/` — the actual app (TanStack Start + React + TypeScript). All app commands run from here.
- `supabase/` — a local Supabase CLI project (`supabase/config.toml`). No migrations/schema exist yet — the app currently runs entirely on frontend-only dummy data (see Data layer below). The root `package.json` exists only to hold the `supabase` CLI as a dev dependency.

## Commands

Run from `frontend/`:

```sh
npm i               # install
npm run dev         # start dev server (vite dev)
npm run build       # production build
npm run build:dev   # build in development mode
npm run preview     # preview a production build
npm run lint        # eslint .
npm run format      # prettier --write .
```

Run from repo root, for the local Supabase stack:

```sh
npx supabase start
npx supabase stop
```

There is no test suite/framework configured in this repo (no test script, no test files).

## Routing (TanStack Start)

File-based routing under `frontend/src/routes/` — see `frontend/src/routes/README.md` for the full convention table. Key points:

- Every `.tsx` file directly under `routes/` is a route; there is no `src/pages/` (Next.js) or `app/` (Remix) convention here.
- Dotted filenames express nesting/dynamic segments, e.g. `customers.$customerId.tsx` → `/customers/:customerId`, `inventory.index.tsx` → `/inventory`, `sales.$invoiceId.edit.tsx` → `/sales/:invoiceId/edit`.
- `routes/__root.tsx` is the single app shell (wraps every page via `AppShell`, provides `QueryClientProvider`, `ThemeProvider`, the 404/error boundary components, and the `<Outlet />` that all other routes render into). Don't remove the `<Outlet />`.
- `src/routeTree.gen.ts` is auto-generated by the TanStack router plugin — never hand-edit it.

## Data layer — being migrated feature-by-feature to Supabase (Phase 1.5)

Per `/business-app-spec.md` section 9, the dummy in-memory data is being replaced one module at a time, in dependency order: Inventory (done), Customers (done), Sales & Invoicing (done), Expenses (done), POS (done), Dashboard & Reports (done), Auth & Roles (done), Audit Log (done), Manager PIN (done), Bulk Import/Export (done — an audit session, see below), End of Day Reconciliation (done — a new, eleventh session, added after the original ten were complete). Remaining Phase 1.5 work is Settings (never itself one of the numbered sessions, see above) plus whatever the deferred-items list still has open.

**`settings` is the only module still on the original two-file pattern** in `frontend/src/data/` (a plain constants file + a `*-store.ts` wrapping it in a module-level `state` object via `useSyncExternalStore`), and it's expected to stay that way — Settings isn't itself one of the ten spec sessions (see the list above); it's Phase 3 scope (the real branch switcher lives there too), and every session so far has deliberately left it local rather than pulling it forward. The two narrow exceptions — `expense_categories` (Session 4) and `business_settings.vat_rate` (the Session 3 follow-up) — were carved out only because a database function needed a trustworthy source for something client input couldn't be trusted for, not because Settings itself needed migrating. Company profile, document/paper settings, date format, currency, low-stock defaults display, and the rest of `useDocumentSettings()` all remain `localStorage`-only; don't start migrating them ahead of a real Settings session.

`settings-store.ts` persists to `localStorage` (`persist()`/`hydrate()`, key `wilelik.document-settings`) — it survives a page reload in the same browser, unlike the old pre-migration `pos`/`expenses` dummy stores, which were pure in-memory and lost everything on reload. Don't confuse the two: `localStorage`-backed is still not Supabase-backed, and no sync between the two exists or is planned before Phase 3.

**Inventory is migrated** — `frontend/src/data/inventory-store.ts` now reads/writes Supabase (`branches`, `products`, `stock_movements` tables). It keeps the original `useInventory()` hook shape (`{ products, defaultThreshold }`) so unrelated consumers didn't need any changes — mutators (`addProduct`, `addProducts`, `adjustStock`, `setProductThreshold`, `setDefaultThreshold`) are now async but still update the same shared store state on completion, so fire-and-forget callers keep working. `Product.category`/`Product.unit` stay typed as the `Category`/`Unit` unions from `data/inventory.ts` even though the DB columns are free text — Settings' editable category/unit lists (`settings-store.ts`, still local/Phase 3) already let staff add values outside that union, so the boundary is trusted at the Supabase row-mapping function in `inventory-store.ts`, same trust level the UI already had.

The nullable-per-row-override-with-a-global-default pattern (`Product.threshold: number | null` + `effectiveThreshold(product, defaultThreshold)`) is preserved: the override lives on `products.low_stock_threshold`, the default on `branches.default_low_stock_threshold`. Replicate this shape at the DB layer for any future nullable-override field rather than inventing a new one.

**Customers is migrated** — `frontend/src/data/customer-store.ts` reads/writes Supabase (`customers` table) and exposes `useCustomers()` / `addCustomer()` / `addCustomers()`. `Customer.orders` and `Customer.payments` were both dropped from the `Customer` type entirely rather than migrated as stored fields — a customer's order and payment history are derived at the route level in `customers.$customerId.tsx` by filtering `useSales().invoices` by `customerId` and flat-mapping their `payments`, not stored redundantly. `customer_payments` (a Session 2 table) was dropped in the Session 3 migration once real invoices existed to derive payment history from instead — nothing had ever written to it (the customer profile's "Record payment" button was always inert), so there was no real data to migrate.

**Sales & Invoicing is migrated** — `frontend/src/data/invoice-store.ts` reads/writes Supabase (`invoices`, `invoice_lines`, `invoice_payments` tables) and exposes `useInvoices()` / `createInvoice()` / `updateInvoice()` / `addPayment()`. `sales-store.ts` is now a pure delegator with no state of its own: `useSales()` combines `useInvoices()` + `useCustomers()` into `{ invoices, customers, vatRate }`, and re-exports `addCustomer`/`addPayment`/`createInvoice`/`updateInvoice` so every existing import path (`import { useSales } from "@/data/sales-store"`) still resolves unchanged. Notable departures from the Inventory/Customers precedent, each with a reason:
- `invoices.id` is `text`, not `uuid` — invoice numbers ("INV-26080001") are a human-facing sequential business identifier used in URLs and print/export, not a surrogate key, so the products/customers uuid convention doesn't apply here.
- `Customer.balance`/`lifetime_total` are kept correct via an `AFTER INSERT OR UPDATE OR DELETE` trigger on `invoices` (`sync_customer_totals()`) rather than an explicit RPC call like `adjust_product_stock()`. Invoices have several write paths (create, edit, record payment, bulk import) and a trigger can't be forgotten by a future call site the way a "remember to call the sync function" convention could be; it also correctly handles an invoice being reassigned to a different customer (recomputes both the old and new customer).
- The stale dummy `customerId`/`productId` references flagged after Sessions 1–2 are resolved for invoices: the Session 3 seed data reseeds all 12 dummy invoices against real customer and product UUIDs, with `total`/`amount_paid`/`balance` hand-computed from `invoiceTotals()` to match exactly. `sales.$invoiceId.index.tsx` and `sales.$invoiceId.edit.tsx` also switched from `throw notFound()` to the same inline "no longer exists" block Sessions 1–2 use for `inventory.$productId.tsx`/`customers.$customerId.tsx` — `notFound()` would otherwise transiently 404 while `invoices` loads asynchronously on first render.

**A same-day follow-up fixed two real bugs in the invoice save path** left over from Session 3's `save_invoice()` (now removed), before Session 4 (Expenses, below) started:
- Session 3's client-side `nextInvoiceId()` read/computed/wrote the next number as three unsynchronized steps, and `save_invoice()` was `insert ... on conflict (id) do update` — so two near-simultaneous creates could mint the same id and the second call would silently overwrite the first invoice's header and delete+replace its line items, no error. Fixed by splitting into two structurally distinct RPCs: `create_invoice()` (no `p_id`/`p_total` parameters at all — the client cannot supply either) always does a plain `insert` and generates its own number from a new `invoice_number_counters` table (one row per `YYMM`, incremented atomically via `insert ... on conflict ... returning` in the same transaction as the invoice insert, so concurrent calls can never collide) in the format `INV-YYMM####`, resetting monthly; `update_invoice()` requires an existing `p_id` and does a plain `update`, raising if the row isn't found. Neither can be coerced into the other's behavior — verified under real concurrency (5 parallel `create_invoice()` calls each got a distinct number) and by forcing the counter table out of sync with actual rows (raises `unique_violation` rather than overwriting).
- `save_invoice()` also trusted a client-submitted `total` outright. `create_invoice()`/`update_invoice()` now compute it themselves via `compute_invoice_total()`, a SQL port of `invoiceTotals()` (`data/invoices.ts`) — same formula, same rounding (round only at the VAT and total steps, nothing in between). `create_invoice()` reads `vat_rate` from a new singleton `business_settings` table rather than trusting the client for that either (a stand-in for the not-yet-migrated Settings module, confirmed at investigation time to still be `localStorage`-only); `update_invoice()` keeps the invoice's own already-issued rate instead of re-reading it, since a rate change shouldn't rewrite an already-issued invoice's math. `invoice-form.tsx`'s "VAT rate" field is now display-only (disabled input, sourced from `useSales().vatRate` for new invoices or `existing.vatRate` for edits) since the server no longer accepts a client-chosen rate for either path.

**Expenses is migrated (Session 4)** — `frontend/src/data/expenses-store.ts` reads/writes Supabase (`expenses`, `expense_categories` tables, plus a `receipts` Storage bucket) and exposes `useExpenses()` (returning `{ expenses, categories }`) / `createExpense()` / `setExpenseCategories()`. `findExpense()` keeps its original signature. Notable decisions, each with a reason:
- `create_expense()` follows the same insert-only discipline as `create_invoice()`: no `p_id` parameter, plain `insert` (never upsert), id generated server-side. Numbering doesn't reset monthly like invoices do (no spec requirement for it), so instead of a counter table it uses a plain Postgres `sequence` (`expense_number_seq`, started one past the highest dummy id) — a sequence's `nextval()` is already atomic under concurrency, so there's no need for the counter table's insert/update dance. There is no `update_expense()`: nothing in the UI edits or deletes an expense once recorded (an append-only ledger), so `create_expense()` is the only entry point — verified under concurrency (5 parallel calls, 5 distinct ids) the same way invoices were.
- Receipt images move from a `receiptDataUrl` (a full base64 `data:` URL held only in browser memory) to a real Supabase Storage bucket (`receipts`, declared public, 3 MB/image limit, image MIME types only). `expenses.receipt_path` stores the object key, not the image; `Expense.receiptUrl` (renamed from `receiptDataUrl`) is a ready-to-use public URL computed once in `mapExpenseRow` via `supabase.storage.from("receipts").getPublicUrl()`, so display sites (`expenses.index.tsx`, `expenses.$expenseId.tsx`) needed only a field rename. `storage.objects` has RLS enabled by default regardless of a bucket's `public` flag — `public` only bypasses RLS for downloads, not uploads — so the migration also adds a policy scoped to the `receipts` bucket granting `anon`/`authenticated` full access, matching this phase's no-auth-yet trust level rather than leaving uploads permanently broken.
- The editable expense category list — previously `Settings`' `expenses.categories` (`localStorage`-only, like the rest of Settings) — is the one piece of Settings pulled into this migration, into a new branch-scoped `expense_categories` table (`branch_id`, `name`, `position`). `expenses.category` stays plain text with no FK to it, matching the Settings UI's existing promise that "removing a category leaves existing expenses untouched." `set_expense_categories(p_branch_id, p_categories)` does a full delete+reinsert in one transaction, matching the `ListEditor` component's existing UX (it always submits the complete desired list, not one add/remove at a time) — this is an intentional state-replace operation, not a record-creation one, so the create/update-can't-collide discipline above doesn't apply to it the same way. `ExpenseSettings`/`updateExpenseSettings` were removed from `settings-store.ts` entirely (not left as dead fields) now that this one list has a real backing table; the rest of Settings is untouched and still local until its own Phase 1.5 session.
- The Dashboard's Cash on Hand KPI (`data/dashboard.ts`) needed no formula change — `cashFromInvoices + cashFromTill - cashExpenses` was already the correct net calculation before this session, just running against dummy expense data. Since `useExpenses()` kept its `{ expenses }` shape (with `amount`/`method` unchanged), the KPI now nets real cash payments against real cash expenses automatically. Verified live: recording a GHS 100 cash expense moved the dashboard's Cash on Hand figure down by exactly GHS 100.

**POS is migrated (Session 5)** — `frontend/src/data/pos-store.ts` reads/writes Supabase (`sales`, `sale_lines`, `sale_payments`, `sale_returns` tables) and exposes `usePosSales()` / `createPosSale()` / `createPosReturn()`. The dummy `posSales` curated array and the entire `pos-history.ts` deterministic historical generator are gone — nothing imported them once the store moved to Supabase, so (matching the Sessions 2–4 precedent) they were deleted rather than left as dead code; `data/pos.ts` now holds only the `PosSale`/`PosLine`/etc. types and the pure `posTotals()`/`discountAmount()`/etc. math, which the checkout page, returns page, receipt components, dashboard, and reports all still import unchanged.
- `create_sale()` follows the create-can't-overwrite discipline exactly: no `p_id`/`p_total` parameters, a plain `insert`, receipt numbers generated server-side from a monthly `sale_number_counters` table (`POS-YYMM####`, same shape as `invoice_number_counters`) — there is no `update_sale()` at all (not even one requiring an existing id, the way `update_invoice()` exists): a POS receipt is an immutable append-only record once rung up, so insert-only is the whole story, not half of a create/update split. `compute_sale_total()` is a SQL port of `posTotals()` (per-line discount capped at that line's own gross, sale-level discount capped at the subtotal, VAT prorated across only taxable lines by the post-discount ratio, rounding only at the VAT and total steps), reading `vat_rate` from `business_settings` the same way `create_invoice()` does.
- Stock deduction reuses `adjust_product_stock()`'s row-lock discipline but goes further: `create_sale()` locks every line's product row (`for update`, in a stable `product_id` order to avoid deadlocking against another sale touching the same products in a different order) and checks *all* lines have sufficient stock *before* deducting *any* of them, all inside one transaction. This closes the gap the original client-side "don't oversell" guard (added earlier as an explicit stopgap, per that task's own description) could never close on its own — a check in JS and the deduction in Postgres are two separate moments a second concurrent sale can slip between. That guard is gone from `pos.index.tsx` entirely now (not layered on top of the real fix): `checkout()` just calls `createPosSale()` and surfaces whatever error Postgres raises (`"Insufficient stock for %"`) via a toast. Verified under real concurrency: 5 parallel 3-unit sales against 9 units of stock — exactly 3 succeeded, exactly 2 raised, final stock landed at exactly 0.
- `create_sale_return()` uses the same check-then-adjust shape for returns/exchanges: it locks the returned product and (if any) the replacement product together in stable `id` order (so an even exchange in one direction and the reverse exchange in another sale can never deadlock each other), restores the returned quantity, and — only if a replacement was chosen — deducts the replacement's stock under the same lock, all atomically. `approval_state` (`'Not required'` / `'Pending manager approval'`) is accepted as a plain parameter from the client and stored as-is — there is no server-side authorization check gating it (real enforcement is Manager PIN, Session 9); the column and the "Needs manager approval" UI in `pos.returns.tsx` are both intentionally just placeholders for now, per the spec's phase ordering.
- Seed data reproduces the old dummy POS dataset faithfully rather than dropping it: the 6 curated `posSales` entries were reseeded against real customer/product UUIDs (preserving each line's own historically-recorded `unitPrice`, which in a couple of cases legitimately differs from that product's *current* price in `products` — the same snapshot-not-live-reference principle already established for invoice lines in Session 3), and the ~305-sale deterministic `pos-history.ts` generator (mulberry32 PRNG, same seed) was re-run once with real UUIDs substituted in to produce static seed rows, rather than porting the PRNG into PL/pgSQL — this keeps `seed.sql` fully static/reviewable while still giving the dashboard's 12-month revenue chart real multi-month data (verified: chart renders a real area path across all 12 month ticks after reseeding). Neither the curated nor historical seed rows touch `products.stock` — like every prior session's seed data, they're treated as history that already happened before the Session 1 stock snapshot, not new sales that should deduct anything.

**Dashboard & Reports is migrated (Session 6) — with no new tables, migrations, or RPCs.** `data/dashboard.ts`'s `useDashboard()` and `data/reports.ts`'s `useReports()` were already pure `useMemo` derivations over `useInventory()`, `useSales()`, `usePosSales()`, and `useExpenses()` — real Supabase-backed stores since Sessions 1–5 — with no dummy dataset of their own to migrate; every session that came before this one preserved those hooks' shapes specifically so downstream consumers (including this one) would pick up real data automatically. This session was an audit to confirm that was actually true rather than assume it, plus fixing what the audit found:
- Checked for markers (`TODO`/`mock`/`placeholder`/etc.), hardcoded numeric literals in `currency()`/`value:` call sites, and `Math.random()` across `dashboard.ts`, `reports.ts`, `reports.tsx`, and `index.tsx` — none found. Read every one of the 11 report definitions in `reports.tsx` (`sales-summary`, `profit`, `expenses`, `operating-margin`, `debtors`, `products`, `valuation`, `discounts`, `vat`, `payments`, `returns`) end to end; every stat, chart series, and table column traces back to a `useReports()` field. Verified live: all 11 render non-placeholder figures against the real seeded data (e.g. Profit & Margin's gross profit at GHS 57,846, VAT Summary's effective rate at 20.0%), with zero console errors.
- Found and fixed two violations of the "never bare 'profit'" naming rule that had nothing to do with data-wiring: the Gross margin stat's hint read "Profit as a share of revenue" (now "Gross profit as a share of revenue"), and Inventory Valuation had a stat labelled "Potential profit" (now "Potential gross profit", since it's retail value minus cost — the same gross-margin concept, just projected onto stock on hand rather than realized sales).
- Found one genuine hardcoded, non-data-driven value: the dashboard header's `description` was the literal string `"Tuesday, 28 July 2026 · Accra Main Branch"`, not derived from the `TODAY` constant every other "today" reference in the app already uses (`reports.ts`'s date presets, `record-expense-dialog.tsx`'s default date, `export-data.ts`'s filenames). Fixed by formatting `TODAY` the same way at render time (`toLocaleDateString` with `weekday`/`day`/`month`/`year`), producing the identical string today but staying correct if `TODAY` ever changes. This session judged `"Accra Main Branch"` itself an acceptable hardcode ("a consistent, deliberate app-wide convention for the single-branch phase, not a data-wiring gap") — **that call was reversed the same day**; see below.
- Confirmed `TODAY` itself (`data/dashboard.ts`, a fixed `"2026-07-28"`) is not in scope to change to `new Date()`: every module's seed data is dated around it, and swapping to the real wall-clock date would make date-range presets, ageing, and "Today's Sales" empty out against dummy history rather than fix anything — this is a demo-data convenience already relied on consistently elsewhere, not a placeholder introduced by this session's module.

**The "hardcoded branch name is fine for the single-branch phase" call above was wrong and was reversed the same day.** The single-branch-vs-real-switcher distinction the Business Domain Rules draw ("Do not build... the real branch switcher... those are Phase 2/3") is about the *feature* of switching between branches, not about whether the one branch's *name* is allowed to be a string literal typed into a dozen files. A literal can't reflect a rename made in `branches.name`; a query can, with zero new UI and no switcher. `frontend/src/data/branch-store.ts` now exposes `useCurrentBranch()` — a small `useSyncExternalStore` hook (same shape as every other `*-store.ts`) that fetches the single `branches` row's `id`/`name` once and caches it in shared module state. Every hardcoded `"Accra Main Branch"` across the app (`topbar.tsx`, `index.tsx`, `pos.tsx`, `pos.index.tsx`'s receipt draft, `sales.index.tsx`, `customers.index.tsx`, `inventory.index.tsx`, `add-product-dialog.tsx`, `import-invoices-dialog.tsx`, `settings.tsx`'s Branches tab, `invoice-form.tsx`) now reads `branchName ?? "…"` from this hook instead. The two dummy data files that also hardcoded the string (`data/inventory.ts`'s `products` array, `data/invoices.ts`'s `invoices` array) turned out to be fully dead code already — nothing had imported either since their modules were migrated in Sessions 1 and 3 — so they were deleted outright rather than patched, taking `BRANCH`/`unitLabel`/the `line()` helpers with them; the still-live `Unit`/`Category`/`Product`/`StockMovement`/`Invoice`/`invoiceTotals()` exports in those two files were untouched.
  - `useCurrentBranch()` needed its own `getServerSnapshot` (returning a fixed `{ id: null, name: null, loading: true, error: null }`, distinct from the live `getSnapshot`) — the same fix `settings-store.ts` already uses, for the same reason. Without it, SSR intermittently threw React hydration-mismatch errors on pages where the branch name renders as part of the very first paint: the server-rendered HTML and the client's first hydration pass could disagree if the store's async fetch resolved during that narrow window, since passing the live `getSnapshot` as both arguments (this file's original mistake) gives React no fixed value to reconcile hydration against. Verified this actually fixed it (not just theorized): a scripted browser check across `/`, `/customers`, `/inventory`, and `/pos` showed real hydration errors before the fix and none after, run several times each to rule out coincidence.
  - Verified the actual ask, not just that the code compiles: renamed the seeded branch row directly in Postgres (the same effect as renaming it through Supabase Studio's table editor) to `"Kumasi Central Depot"`, then loaded every page listed above in a real browser and confirmed each one displayed the new name with no code change, before restoring the seed value back to `"Accra Main Branch"`.
  - One unrelated, pre-existing bug surfaced during this verification and was left alone as out of scope that session: `/pos`'s live receipt preview occasionally hydration-mismatched on its own, because `pos.index.tsx`'s `today()`/`now()` called `new Date()` directly during render with no SSR guard — if the server render and the client's hydration pass straddled a minute boundary, the clock string differed by a minute. **Fixed in a same-day follow-up**, same technique as `useCurrentBranch()`'s `getServerSnapshot`: `today()`/`now()` are no longer called during render at all. A `draftClock` state (`{ date, time } | null`) starts `null` — identical on the server and on the client's first hydration pass — and is only ever populated from a `useEffect` (client-only, runs after hydration commits, refreshed every 30s so the preview doesn't visibly go stale while a cashier builds a long cart), with the `ReceiptPreview` draft falling back to `"…"` in the meantime, the same placeholder convention `branchName ?? "…"` already established. Verified the fix, not just the theory: the same scripted hydration check that had caught this flaking roughly 1 run in 4 before now passes 4/4 fresh `/pos` loads in a row, plus a full sweep of `/`, `/customers`, `/inventory` showing no regressions.

**Auth & Roles is migrated (Session 7).** Supabase Auth (self-hosted GoTrue) now backs real staff logins. `frontend/src/data/auth-store.ts` exposes `useAuth()` (`{ session, staff, loading, error }`) plus `signIn()`/`signUp()`/`signOut()`; every route is wrapped in `<AuthGate>` (`components/auth/auth-gate.tsx`, mounted in `__root.tsx`) which redirects to `/login` once `!loading && !session`, and shows an "account not active" state if a session exists but its `staff` row doesn't (or is inactive) rather than treating any authenticated session as sufficient. A new `staff` table (`id` = `auth.users.id`, `branch_id`, `name`, `email`, `role` checked against `'Attendant' | 'Manager' | 'Accountant/Auditor'`, `active`) is the roster; `frontend/src/data/staff-store.ts` (`useStaff()`, `setStaffRole()`, `setStaffActive()`) backs a new Staff tab in Settings, UI-gated to Managers (`currentStaff?.role === "Manager"`) — as with every other client-side gate in this app, the real enforcement is server-side RLS (`staff_update`'s `has_role(['Manager'])`), not the UI hiding the controls.
- Every "who did this" free-text column flagged since Session 1 — `stock_movements.performed_by`, `invoices.issued_by`, `invoice_payments.recorded_by`, `expenses.recorded_by`, `sales.cashier` — is now a real `uuid references staff(id) on delete restrict`, plus a brand new `sale_returns.processed_by` column (`create_sale_return()` used to hardcode `'System'`, with no way to attribute a return to a real person at all). None of these accept a client-supplied value any more: every create RPC (`adjust_product_stock`, `create_invoice`, `update_invoice`, `record_invoice_payment`, `create_expense`, `create_sale`) dropped its `p_performed_by`/`p_issued_by`/`p_recorded_by`/`p_cashier` parameter entirely, and a `before insert` trigger on each table (`set_performed_by()`, `set_issued_by()`, etc.) unconditionally overwrites the column with `auth.uid()` whenever there is an authenticated caller — deliberately at the trigger level rather than only inside the RPCs, because `inventory-store.ts`'s `addProduct()`/`addProducts()` insert into `stock_movements` directly via PostgREST, bypassing `adjust_product_stock()` entirely, so an RPC-only fix would have missed them. Each column also carries a `default auth.uid()`, added purely so the generated `Insert` TypeScript types mark it optional (letting the frontend omit it, the way `NewProduct`/`NewInvoice`/etc. now do) — the default is not the security boundary, since a client that explicitly sends someone else's uuid would sail straight past a default; the trigger is what actually blocks spoofing, verified live by inserting a `stock_movements` row with `performed_by` explicitly set to a different staff member's uuid and confirming the row landed attributed to the signed-in caller instead.
- `is_active_staff()`, `has_role(p_roles text[])`, and `require_staff()` (the guard every create RPC above now starts with) are all `security definer` with `set search_path = public` — without it, `staff`'s own `staff_select` RLS policy calling `is_active_staff()`, which itself queries `staff`, is a self-referential loop. This was caught as a real `"stack depth limit exceeded"` error while testing `create_expense()` as an authenticated Manager, not reasoned out in advance, and is documented as load-bearing directly in the migration.
- The signup trigger (`handle_new_staff_signup()`, `after insert on auth.users`) auto-promotes the very first signup ever to Manager (`not exists(select 1 from staff)`) and defaults every signup after that to Attendant — deliberately never reading a client-supplied `role` out of signup metadata, closing an obvious privilege-escalation hole. Verified live: a signup request with `"role":"Manager"` in its metadata, sent against a roster that already had staff, still landed as Attendant.

**Audit Log is migrated (Session 8) — backend-only, no new frontend route.** business-app-spec.md scopes this session to exactly "table plus logging wired into every discount, VAT override, and return," with no UI page named for it (that's consistent with the session plan: Session 9, Manager PIN, is the next one that touches UI). `supabase/migrations/20260803150000_audit_log_schema.sql` adds `audit_log` (`branch_id`, `actor_id`, `action` checked against `'discount_applied' | 'vat_override' | 'return_processed'`, `entity_table`, `entity_id`, `before`/`after` jsonb, `occurred_at`) plus five `AFTER INSERT`/`AFTER UPDATE` trigger functions on the tables where those actions actually happen — never an extra `insert` bolted onto the RPCs themselves, per this session's explicit brief ("entries only ever get created by triggers on the actions themselves, never inserted by client code"). This matches the precedent Session 7 already set for identity columns: a trigger is the only place that catches every write path to a table at once, RPC or direct (`inventory-store.ts`'s `addProduct()`/`addProducts()` still write to `stock_movements` directly, bypassing `adjust_product_stock()` entirely — an RPC-only audit hook would have the same blind spot an RPC-only identity hook would have had).
- **What's logged and why:** `invoices.invoice_discount` (on insert when non-zero, on update whenever it changes — including changing back to zero, since removing a discount is still a change worth logging); `invoice_lines.discount`/`invoice_lines.vat` (on insert only — logged as `discount_applied`/`vat_override` whenever a line lands with a non-zero discount or `vat = false`); `sales.sale_discount_value`/`sales.vat_mode` (insert-only, since sales have no update path at all — `vat_mode <> 'per-item'` is the whole-sale VAT override the spec's "toggle... for the whole sale" describes); `sale_lines.discount_value`/`sale_lines.vat` (insert-only, same shape as invoice lines); and `sale_returns` (logged unconditionally on every insert — every return is inherently sensitive per this session's own title, not just the cash-refund path `create_sale_return()` already gates). Deliberately *not* audited: an invoice's own `vat_rate` (fixed at issue time, `update_invoice()` never rewrites it) and `business_settings.vat_rate` (changing the configured default is a distinct settings action, not a per-sale/per-item "override" — the word this session actually uses).
- **`invoice_lines` only ever gets an `AFTER INSERT` trigger, never `AFTER UPDATE`, and its audit rows never carry a `before` value** — `update_invoice()` deletes and re-inserts the full line set on every edit (see the `invoice_create_update_split` migration), so by the time a line lands via `INSERT`, whatever it looked like before is already gone from the table; there's no `OLD` row left to diff against. Every insert (create *or* edit) that lands a line with a non-zero discount or a false VAT flag gets logged as an "as of this save" snapshot attributed to whoever performed it, not a diff against that line's own history — genuinely doing better would mean redesigning `update_invoice()` away from delete-and-reinsert, which is out of scope here.
- **Actor attribution is `coalesce(auth.uid(), <the row's own already-resolved identity column>)`, not a bare `auth.uid()`.** For the insert-only tables (`sales`, `sale_lines`, `sale_returns`) this is exactly right either way — a live request always has `auth.uid()` (`require_staff()`/`require_writable_role()` already reject anyone without it) — but the fallback is what makes `seed.sql` produce a real, attributed historical audit trail for free: seed data runs as the postgres superuser with no `auth.uid()` at all, so the trigger falls back to whatever staff uuid `seed.sql` already attributed the row to (`cashier`/`processed_by`), with no separate `audit_log` seed rows needed. For `invoices` specifically (which *does* have an update path), `auth.uid()` is what's wanted on an edit — `issued_by` is fixed to the original creator and `update_invoice()` never touches it, so falling back to it on a live edit would misattribute the edit to the original issuer; the fallback is only ever meant to catch the no-JWT superuser context, not something a real edit should reach.
- **`audit_log` gets no `insert`/`update`/`delete` grant for anyone — not `anon`, not `authenticated`, not even `service_role`**, a deliberate, documented exception to the "`service_role` always gets full CRUD" convention two paragraphs below. That convention's own justification is "`service_role` already bypasses RLS by role attribute, so holding back its grant buys no real security" — but RLS bypass and table `GRANT`s are separate layers, and `audit_log`'s security property specifically depends on the `GRANT` layer, since the `SECURITY DEFINER` trigger functions write to it regardless of what's granted to the calling role. `service_role` is local-tooling-only today (only local scripts authenticate as it), and there's no legitimate reason any tooling script should ever need to fabricate an `audit_log` row by hand. Verified live: a Manager's direct `POST`/`DELETE` against `audit_log` both come back a plain `42501 permission denied for table audit_log` — not even reaching an RLS check, since there's no grant to evaluate one against.
- **No `delete` policy at all, for any role — including Manager**, despite section 6's literal "Manager: read and write on every model, including delete... everything." An audit log a Manager can quietly delete rows from (including rows logging that same Manager's own discount overrides) isn't a trustworthy audit log, which is the entire point of building one. This mirrors a precedent already in this codebase: `staff` has no delete policy either, specifically because "the audit trail must never lose its subject" — this applies the same principle to the log itself rather than to the things it logs. Verified live: deleting the invoice an audit row refers to (a plain Manager-permitted `invoices` delete) leaves that row's `audit_log` history completely intact, since `entity_id` is a plain text reference, not a foreign key back to the table it describes.
- **Read access is Manager and Accountant/Auditor only, not the `is_active_staff()` every ordinary operational table's `select` policy uses** — the spec's Roles table doesn't put an audit trail of *other* staff's discount/VAT/return actions in Attendant's granted module list, so this gets the same treatment as Reports (see the role-permissions-rewrite entry above: "must stay off-limits to Attendants entirely... that's not the same as \[an Attendant's] own sales history"). Verified live, signed in as each seeded local-dev account: Manager and Auditor both read all 14 seeded rows; Attendant gets `Content-Range: */0` (zero rows, not a 4xx).
- **Verified end-to-end against the real backend, not just against seed data:** a live `create_invoice()` call (Manager, header discount + a line with both a discount and `vat: false`) produced exactly the three expected `audit_log` rows, correctly attributed to "Dev Manager" via `auth.uid()` rather than the seed fallback; a follow-up `update_invoice()` call dropping that discount back to zero produced a fourth row with `before: {"invoice_discount": 75.00}` / `after: {"invoice_discount": 0.00}`; a live `create_sale()` (Attendant, using the seeded `customer_discounts` row plus `vat_mode: "none"`) and a live `create_sale_return()` (Attendant, Store credit) both produced correctly-attributed rows too. All disposable test rows were cleaned up afterward; the `audit_log` rows describing them were deliberately left in place, since erasing them by hand would contradict the whole feature.

**Manager PIN Authorization is migrated (Session 9) — scoped to POS discount/VAT overrides only, not returns.** business-app-spec.md's Phase 1.5 summary calls for a "Manager PIN/password popup to authorize discount or VAT overrides, and to approve returns." Returns are already handled (the role-permissions-rewrite migration's cash-refund gate), and this session was explicitly told not to build a second, redundant authorization path for that — so the whole of this session is the POS discount/VAT half. `supabase/migrations/20260803160000_manager_pin_authorization.sql` adds the schema; `frontend/src/data/manager-override.ts` + `frontend/src/components/pos/manager-override-dialog.tsx` add the popup.
- **Password, not a PIN** — reuses real Supabase Auth email+password (the same mechanism `/login` already uses), not a new PIN scheme. GoTrue has no PIN grant type and can't hand back a real, verifiable session token for one; a PIN would mean inventing a parallel, weaker authentication path (a `staff.pin` column, custom hashing, and a way to turn "PIN matched" into something a signed RPC call can trust) for zero benefit over what already exists and is already battle-tested (Session 7).
- **The mechanism:** the Attendant's browser asks for a Manager's email+password in a dialog, then makes a plain `fetch` call directly to GoTrue's password-grant endpoint — deliberately bypassing the shared `supabase` client entirely, so the app's persisted session/localStorage never changes and the Attendant's own session is never switched away. That token is spent on exactly one follow-up call, `authorize_manager_override()`, which mints a single-use, 5-minute `manager_overrides` ticket recording which real Manager (`auth.uid()`, unspoofable — forced by the same identity-forcing-trigger discipline used everywhere else in this build, not trusted from client input) approved it, then the token itself is discarded, never persisted anywhere. The Attendant's own, still-fully-signed-in session then calls `create_sale()` as normal, passing the ticket id; `create_sale()` calls `consume_manager_override()` (`SECURITY DEFINER`, the only thing with an `UPDATE` grant on `manager_overrides` at all) to redeem it exactly once. `sales.cashier` is never touched by any of this — the checkout call itself always runs under the Attendant's real session, never the Manager's, so "who rang this up" and "who authorized the override" stay two separate, correctly-attributed facts.
- **`create_sale()` gains a real VAT restriction for non-Managers that didn't exist before this session** — there was nothing to authorize on the VAT side otherwise. Before now, `vat_mode` and a line's `vat` flag were unrestricted for any role; now, for anyone who isn't a Manager and doesn't have a redeemed ticket, `vat_mode` must stay `'per-item'` and every line's `vat` flag must stay `true`, mirroring the discount restriction exactly. The existing discount check and the new VAT check now share one `v_authorized` flag (`has_role(['Manager'])`, or a successfully consumed ticket) instead of the discount check's old standalone `has_role(['Manager'])` test — a Manager needs no ticket at all (matches "applying discounts... everything" being an unqualified Manager grant already); a redeemed ticket lifts exactly the same restrictions a real Manager role would have lifted, for that one `create_sale()` call, and nothing else (not `create_expense()`, not `adjust_product_stock()`, not `create_customer_discount()` — this ticket only ever means anything inside `create_sale()`).
- **`sales.override_authorized_by`** (nullable, `references staff(id)`) is set from the ticket's `manager_id` only when one was actually redeemed; null for an ordinary sale or a Manager's own direct sale. Session 8's `audit_sale_header()`/`audit_sale_line()` triggers now derive their actor as `coalesce(override_authorized_by, auth.uid(), cashier)` instead of `coalesce(auth.uid(), cashier)` — for a Manager's own sale this changes nothing (`override_authorized_by` is null, `auth.uid()` already correctly resolves to that Manager); for a ticket-authorized Attendant sale, `auth.uid()` during `create_sale()` is the Attendant (they're the one who called it) — exactly the misattribution this session exists to prevent — so `override_authorized_by` has to be checked first.
- **Why a ticket table instead of a client-supplied `manager_id` parameter:** a bare uuid parameter is exactly the kind of spoofable client input Session 7 already eliminated everywhere else in this build (an Attendant could just type in any Manager's id). A ticket minted via a real, freshly-verified Manager JWT — where `manager_id` is forced from that JWT's own `auth.uid()`, never trusted from client input — is the only way to make "a Manager actually approved this" a claim the database itself can verify. `manager_overrides.requested_by` (who asked for it) is the one field that *isn't* independently verified at mint time — the RPC that inserts it runs under the Manager's token, which has no way to know the Attendant's identity (different JWT, different request) — but it becomes a real check at redemption time instead: `consume_manager_override()` only redeems a ticket for the session whose `auth.uid()` matches `requested_by`, so a mis-declared or leaked ticket id still can't be redeemed by anyone else. Verified live: a ticket requested for one attendant, redeemed directly by a different signed-in staff member's token, is rejected with the same generic "invalid, already used, or expired" message a truly bad ticket id would get.
- **`manager_overrides` gets no `update`/`delete` grant for `authenticated` at all** — the same "nothing outside its own controlled function can write to this" shape Session 8 used for `audit_log`, here applied to a table that's mutable (rather than append-only) but still shouldn't be directly writable: only `consume_manager_override()` (`SECURITY DEFINER`) can ever flip `used_at`. Unlike `audit_log`, `service_role` *does* get full CRUD here (matching the standard "every new table" convention) — there's no `audit_log`-style "even the most privileged role shouldn't touch this" argument for a short-lived, self-expiring authorization ticket, and this table doesn't carry the audit_log's own tamper-evidence goal.
- **Verified live against the real backend, not just that the popup renders:** unauthorized attempts to apply an arbitrary discount, override whole-sale VAT, or turn off a line's VAT — each with no ticket — were all correctly rejected with the new, specific error messages; a Manager-minted ticket, redeemed by the Attendant, unlocked all three in one `create_sale()` call, produced `sales.cashier` = the Attendant and `override_authorized_by` = the Manager, and the resulting `audit_log` rows (`discount_applied`, `vat_override`) were both correctly attributed to the Manager, not the Attendant. Reusing the same (now-used) ticket, consuming a ticket requested for a different staff member, and consuming a manually-expired ticket were all rejected with the same generic message; a raw `PATCH` against `manager_overrides` came back a bare `42501` (no grant exists for it at all, so it never even reaches an RLS check). `tsc --noEmit`, lint, and build all pass clean. No browser tool was available in this environment to click through the popup interactively — the popup's own logic (state gating, ticket lifecycle, what it sends to `createPosSale()`) was verified by careful reading rather than an interactive click-through; say so rather than claim a browser check that didn't happen.

The spec's own field list for the close action — counted cash, manual tally figures, note — pointedly omits opening float, confirming it's a separate morning action rather than a close-time input, so the row transitions open → closed exactly once rather than being created fully-formed. - **Found and fixed a real bug during verification, not just in code review:** `close_day()`'s original state check used `select ... for update` to lock the row before updating it. Postgres RLS applies the *UPDATE* policy's `USING` clause to `SELECT ... FOR UPDATE` too (it has to confirm the row is actually lockable) — so once a day was closed, that locking read silently matched zero rows and the function raised "confirm this morning's opening float" instead of "today has already been closed," a real, user-facing wrong-error-message bug that only showed up by actually trying to re-close an already-closed day, not by reading the function. Fixed by using a plain (non-locking) read for the state check and letting the final `UPDATE ... WHERE closed_at IS NULL`'s own row-match (checked via `FOUND` afterward) carry the atomicity guarantee against a concurrent double-close instead.
- **Every figure is scoped by the transaction's own timestamp, not the timestamp of anything it references** — the spec's central correctness rule, and the one this session spent the most verification effort on. `compute_day_totals()` is a day-scoped SQL port of `compute_sale_total()`'s per-line discount/VAT math (duplicated rather than shared, the same call Session 9 made for `compute_day_totals()`'s POS-return-math sibling, to avoid touching a function `create_sale()` depends on for every checkout), plus three further aggregations, each keyed to its own most-specific timestamp: sales-by-payment-method uses `sale_payments.paid_at` (not the parent sale's `sold_at` — in practice the same instant for POS, since a payment is captured atomically with its sale, but this is the literal, defensible reading of the rule, not a shortcut); cash refunds use `sale_returns.returned_at` — the one that actually matters, since a return processed days after its sale must land on the day it happened, not the sale's day; cash expenses use `expenses.date`, the expense's own business date, not `recorded_at`'s insert-time metadata. **Journal Entries & General Ledger is added (Session 13) — the double-entry engine on top of Session 12's Chart of Accounts.** Spec item 13, scoped deliberately narrow: "the core double-entry mechanics, manual journal entry capability, the ledger view, the posting function every automated entry will call. The `/accounting` route guard (Attendant blocked entirely, same as Session 12) moved up from the old single-page `accounting.tsx` into the new shared layout, since it now applies uniformly across all three tabs rather than one page repeating it.
- **Branch-scoped, unlike `accounts`.** Session 12's chart of accounts was deliberately *not* branch-scoped (one company, one ledger structure); `journal_entries` is the opposite case — each row is an individual dated transactional record, the same class of table CLAUDE.md's "branch_id everywhere" rule already targets (products, invoices, sales, expenses). `id` is text (`JE-YYMM####`), not uuid, matching `invoices.id`/`sales.id` — a human-facing sequential identifier shown in the ledger and referenced by reversing entries, not a surrogate key. Numbering reuses the exact `invoice_number_counters`/`sale_number_counters` shape (`year_month text primary key`, `insert ... on conflict ... returning`), including that precedent's own detail of *not* being branch-scoped itself even though the table it numbers is.
- **"Structurally impossible to post an unbalanced entry" is a deferred constraint trigger on `journal_lines`, not a CHECK constraint** — Postgres CHECK constraints are per-row and can't see sibling rows, and "debits = credits" is a property of the whole entry. `check_journal_entry_balanced()` fires on every insert/update/delete but doesn't run until the transaction is about to commit (`deferrable initially deferred`), so `post_journal_entry()` can insert an entry's lines one at a time and only pay the validation once, as a whole, right before commit — and, more importantly, so does *any other write path*, including a raw multi-row insert that bypasses `post_journal_entry()` entirely. `post_journal_entry()` also pre-validates the balance itself, purely for a clear, specific error ("Entry is not balanced: debits X do not equal credits Y") instead of the trigger's more generic one — the same "RPC check is a UX nicety, the constraint/RLS is the real boundary" relationship established everywhere else in this build. Verified live, not just reasoned about: a raw single-row `INSERT` directly against `journal_lines` (as Manager, who has real `INSERT` grant), adding one unbalanced line onto an already-balanced *posted* entry, was rejected at commit time with the row never actually landing — confirmed by re-querying the entry's lines afterward and finding them unchanged.
- **Once posted, immutable — no exception, not even for Manager.** `journal_entries`/`journal_lines` have no `UPDATE` or `DELETE` policy at all, and (a narrower version of the `audit_log` exception to "`service_role` always gets full CRUD, it already bypasses RLS so withholding the grant buys nothing") no `UPDATE`/`DELETE` **grant** either, for any role, `service_role` included. `audit_log`'s reasoning was "a `SECURITY DEFINER` trigger writes to it regardless of grants, so the grant layer is the actual boundary"; that specific mechanism doesn't apply here (there's no trigger forcing inserts), but the underlying goal is the same — "once posted, immutable" is the entire point of this session, and `service_role`'s RLS bypass would otherwise make that false against any local script authenticated as it. There is no legitimate reason a tooling script needs to edit or delete a posted journal entry. Verified live: a direct `PATCH`/`DELETE` against `journal_entries` as Manager both came back a plain `42501`, not an RLS denial — there's no policy to even evaluate.
- **`reverse_journal_entry()` is the one sanctioned correction path**, matching "a mistake gets corrected with a reversing entry, not a change to history" literally rather than just as a UI convention. It composes `post_journal_entry()` (swaps every line's debit and credit, posts that as a new entry, links back via `reverses_entry_id`) instead of duplicating its numbering/validation logic. One reversal per entry — a second reversal attempt is rejected — a judgment call the spec doesn't settle: partial or multiple reversals of one entry add real complexity (which lines does a second reversal touch?) that nothing in this session's scope calls for. `reversedByEntryId` (the inverse of `reverses_entry_id` — "what reversed this," not just "what this reverses") is computed client-side in `journal-store.ts` from the same already-loaded rows, not a second query or a stored column, since it's a pure derivation.
- **RLS matches `accounts`' shape exactly**: Attendant gets none of select/insert on any of the three new tables (Accounting isn't in Attendant's granted module list), Accountant/Auditor is read-only, Manager can post. Neither `post_journal_entry()` nor `reverse_journal_entry()` is `SECURITY DEFINER` — same reasoning as `create_invoice()`/`create_sale()`: they run with the calling Manager's own grants+RLS, so the `INSERT` policies are what actually enforce "Manager can post," not just the functions' own `has_role()` checks (those are the early, clearly-worded UX nicety, matching `require_writable_role()`'s role everywhere else).
- **The General Ledger is computed, never stored** — `ledgerForAccount()` in `journal-store.ts` takes the already-loaded `JournalEntry[]` (with nested lines, each embedding its account's code/name) and one account, filters to that account's lines, sorts by the transaction's own `entry_date` (then entry id as a tiebreak) — chronological order, *not* creation order, standard General Ledger convention — and walks a running balance in the account's own natural terms (`normalBalance === "debit" ? (debit - credit) : (credit - debit)`), so a debit-normal account like Cash reads "balance rises with debits" and a credit-normal account like Sales Revenue reads "balance rises with credits," rather than one global sign convention an accountant would have to mentally flip for half the accounts. **Auto-Posting Integration is added (Session 14) — wires Sessions 1-11's real transactions into automatic journal entries via Session 13's engine.** `supabase/migrations/20260807100000_auto_posting_integration.sql` adds eight `post_..._journal_entry()` functions and threads one `perform` call into each of `create_sale()`, `create_invoice()`, `record_invoice_payment()`, `create_expense()`, `create_sale_return()`, `adjust_product_stock()`, `close_day()`, and `record_bank_deposit()`.
- **Why this doesn't just call `post_journal_entry()`:** that function is deliberately not `SECURITY DEFINER` (Session 13: RLS is the real "Manager can post" boundary, not just its own `has_role()` check), and neither are `create_sale()`/`create_invoice()`/etc, which Attendants call constantly — so a naive `perform post_journal_entry(...)` from inside `create_sale()` would run under the Attendant's own role and hit `journal_entries_insert`'s Manager-only policy on every single checkout. Broadening that policy to `can_write()` was considered and rejected (it would let an Attendant `INSERT` an arbitrary manual-looking entry directly via raw REST, undoing Session 13's actual security property for no reason connected to this session). The design that keeps both intact: eight new `SECURITY DEFINER` posters, each taking only the id of an already-inserted row and deriving every debit/credit itself by re-reading that row's own already-committed-in-this-transaction data — never a free-form line array from its caller. Granting them `EXECUTE` to `authenticated` (required, so `create_sale()` can call one under an Attendant's own role) is safe specifically because of that shape: a direct call by any role can only ever post the one correct entry for a real, existing transaction, and only once (`journal_entries`' new `unique (source_table, source_id)` constraint — see below). Each poster calls a shared private `_post_journal_entry_rows()` (`SECURITY DEFINER`, granted to no one, only reachable from within another `SECURITY DEFINER` function's execution) that duplicates `post_journal_entry()`'s numbering/insert shape rather than calling it, so Session 13's manual-entry security property is never touched by this migration.
- **Atomicity ("a sale and its journal entry either both succeed or both fail") falls out of this for free**, not from any new transaction-management code: each poster call is one more statement inside `create_sale()`'s own `plpgsql` body, in the same implicit transaction as the sale/stock/payment inserts. Verified the hard way, not just reasoned about: pre-inserted a `journal_entries` row colliding with the *next* sale's about-to-be-generated id, then called `create_sale()` — it failed with the collision error, and afterward the product's stock, the sales count, and even `sale_number_counters`' value were all exactly unchanged from before the attempt. The counter increment happening and then rolling back alongside everything else is the clearest possible proof the whole statement sequence is one atomic unit.
- **Idempotency is structural, not a "check first" race**: `journal_entries.source_table`/`source_id` (both nullable — null for every manual entry, `post_journal_entry()`'s signature doesn't even accept them) carry a `unique (source_table, source_id)` constraint. Postgres's default NULLS DISTINCT means many manual entries with `(null, null)` coexist fine; two real attempts to post the same transaction collide for real. Verified live: calling `post_sale_journal_entry()` a second time for an already-posted sale raises `"sales POS-... has already been posted to the ledger"` rather than creating a duplicate.
- **Amounts are anchored to each transaction's own already-computed, already-validated total** (`sales.total`, `invoices.total`, ...) rather than trusting two independently-rounded calculations to agree to the cent. `compute_sale_posting_amounts()`/`compute_invoice_posting_amounts()` duplicate `compute_sale_total()`/`compute_invoice_total()`'s per-line arithmetic (same reasoning Session 11's `compute_day_totals()` used: avoid touching a function every checkout depends on) to get subtotal/discount, round each to 2dp, then derive VAT as whatever residual makes `total = subtotal - discount + vat` hold *exactly* — this isn't a shortcut, it guarantees the posted entry balances against the real, already-collected total by construction, which is what actually matters for a ledger.

**Bank Accounts & Reconciliation is added (Session 16) — the full module this time, not Session 11's lightweight `bank_deposits` log.** Three new tables (`bank_accounts`, `bank_reconciliations`, `bank_statement_lines`) plus seven RPCs (`create_bank_account`, `import_bank_statement_lines`, `start_bank_reconciliation`, `match_statement_line`, `clear_statement_line`, `unmatch_statement_line`, `complete_bank_reconciliation`, `cancel_bank_reconciliation`), a new `/banking` section (Accounts/Reconcile/History tabs, gated the same as Accounting/Reports — Manager full access, Accountant/Auditor read-only, Attendant blocked entirely), and one real fix to a Session 11 gap: `bank_deposits` always posted against a hardcoded `1010 Cash in Bank` regardless of which real bank account received the money; it now carries a real `bank_account_id`, and `record_bank_deposit()`/`post_bank_deposit_journal_entry()` read that account's own `gl_account_id` instead.
- **A bank account is deliberately not branch-scoped**, the same reasoning Session 12 gave the chart of accounts itself: a bank account belongs to the whole legal entity, not to one branch, even once a second branch exists. `gl_account_id` and `opening_balance`/`opening_balance_date` are immutable once set (a `before update` trigger rejects any change, for every role including Manager) — a reconciliation's own math is anchored to these values, and changing them after even one reconciliation exists would silently invalidate its tie-out. A second trigger (`validate_bank_account_gl_link`) rejects linking to anything outside the Assets category, structurally rather than just in the UI's account picker (which itself only offers Assets-category accounts, for a good first impression, not as the real boundary).
- **Reconciliation ties out the same way Session 15's Trial Balance does — structurally, not by convention.** `complete_bank_reconciliation()` refuses to complete unless (1) zero statement lines dated on/before the statement date remain `'unmatched'` — every line has to be actively resolved one way or another, never silently skipped — and (2) `opening_balance` + the sum of every line resolved *in this session* (matched or cleared) equals the entered `statement_ending_balance` to the cent. This is the modern "reconcile-by-matching" model real bank-rec software (Xero, QuickBooks Online) uses, deliberately simpler than the older two-column "outstanding checks/deposits in transit" worksheet: since a `'matched'` line's amount is already asserted equal to its ledger counterpart at match time, and a `'cleared'` line is a Manager's own deliberate, reasoned override, the sum can only fail to tie out if the entered statement balance, the account's opening balance, or the statement import itself is actually wrong — exactly the class of real error this check exists to catch.
- **A rolling opening balance, not a fixed one**: each new session's `opening_balance` is snapshotted at `start_bank_reconciliation()` time from the *previous completed session's* `statement_ending_balance` (or the bank account's own `opening_balance` for the very first session ever) — never recomputed later, the same "fixed at creation" principle as an invoice's own `vat_rate`. A statement line only ever gets its `reconciliation_id` stamped at match/clear time (not at import time), so an old, still-unresolved line from a prior period naturally carries forward into whichever session eventually resolves it, without double-counting anything a previous *completed* session already accounted for.
- **`'matched'` is a strict claim, `'cleared'` is a deliberate, reasoned override — two different things, not degrees of the same action.** `match_statement_line()` requires the ledger line's own signed amount (`debit - credit`; every bank account's `gl_account_id` is Assets/debit-normal by the trigger above, so this sign convention is always correct) to equal the statement line's amount to the cent, and rejects a ledger line already claimed by another statement line (`unique (matched_journal_line_id)`, NULLS DISTINCT so unmatched rows never collide with each other). `clear_statement_line()` is the escape hatch for real bank activity with no ledger counterpart yet (a bank fee not yet expensed, say) — it requires a non-empty reason (`clear_note`), enforced in the RPC, not just encouraged in the UI copy.
- **Identity and status consistency are trigger-enforced, not just RPC discipline**: `set_statement_line_resolution()` (`before update`) forces `matched_by`/`matched_at` on any `unmatched -> matched/cleared` transition and nulls `matched_by`/`matched_at`/`matched_journal_line_id`/`reconciliation_id`/`clear_note` on the way back to `unmatched` — `unmatch_statement_line()` and `cancel_bank_reconciliation()` both lean on this rather than each remembering to null every column themselves. Three CHECK constraints back this up structurally regardless of which code path writes the row: `(status = 'unmatched') = (matched_by is null)`, `(status = 'unmatched') = (reconciliation_id is null)`, and `status = 'matched' or matched_journal_line_id is null`.
- **A raw PATCH bypassing `match_statement_line()`'s amount-equality check is a documented, accepted gap, not an oversight** — only Manager reaches `bank_statement_lines_update` at all (the same role section 6 already grants unrestricted write access "on every model, everything"), and the identity/consistency invariants that actually matter stay trigger-enforced regardless of which path performs the update. The same class of tradeoff already accepted for `products.cost`'s visibility to Attendant.
- **`cancel_bank_reconciliation()` is the one sanctioned way to undo an open session** — resets every statement line it had resolved back to `unmatched` (the resolution trigger above handles the cleanup), then deletes the session row itself, so the `bank_reconciliations_one_open_per_account` partial unique index doesn't leave an account permanently stuck behind a session started by mistake. A *completed* session has no equivalent: no update policy reaches a `completed_at is not null` row, and no delete policy does either — the same "once posted/closed, permanent" rule `journal_entries` and `day_closes` already established, here extended to reconciliation history for the same reason (an audit record its own most-privileged user can quietly erase isn't trustworthy).
- **A real RLS bug surfaced and fixed during live verification, not caught by review**: `bank_reconciliations_update`'s `USING (has_role(['Manager']) and completed_at is null)` had no explicit `WITH CHECK`, so Postgres defaulted it to the same expression — which then also applied to the *new* row, blocking the exact `completed_at is null -> not null` transition the policy exists to allow. `complete_bank_reconciliation()`'s own `UPDATE` failed with a bare `42501` until `WITH CHECK` was given explicitly as just `has_role(['Manager'])`. Found by actually running the full RPC sequence against the local backend before ever opening the browser, the same "verify the mechanism before verifying the screen" discipline this build has relied on since Session 7.
- **Suggested matches are computed client-side, never stored** (`frontend/src/data/bank-matching.ts`) — the same "computed, never stored" precedent `ledgerForAccount()` (Session 13) and `financial-reports.ts` (Session 15) already established. `suggestMatches()` looks for a same-signed-amount candidate within a 7-day clearing-lag window; the Reconcile screen's `<Select>` for each unmatched line lists those first, then every other not-yet-claimed ledger line for the account, so a real match that happens to fall outside the tolerance window is never a dead end. A read-only "Unmatched ledger activity" panel — everything the books show for the account with no statement line matched to it yet — is shown for transparency but never gates completion: an outstanding item (a payment that hasn't cleared the bank yet) is normal and expected to carry forward, not an error to resolve immediately.
- **Deliberately out of scope: no new "withdrawal" transaction type.** Money already leaves `1010` today (a Bank-method expense credits it) and already arrives (Card/Bank Transfer/Cheque payments, and now a deposit, debit it) — "matching deposits and withdrawals" (the spec's own phrase) means a statement line can carry either sign and still be matched against whichever existing ledger activity produced it, not that this session needed to invent a new kind of business transaction.

Started a reconciliation, added four statement lines (three matching the real activity above, one deliberate bank-fee line with no ledger counterpart at all), and confirmed the Complete button stayed disabled — not a server error, a disabled control — while any line remained unmatched, including with only the one deliberate fee line left. **Suppliers & Purchasing is added (Session 17) — a brand new module, no Phase 1 dummy data to migrate.** Six new tables (`suppliers`, `purchase_orders`, `purchase_order_lines`, `purchase_order_receipts`, `purchase_order_receipt_lines`, `supplier_payments`) plus eight RPCs, tied into Accounts Payable (`2000`) the same way invoicing ties into Accounts Receivable (`1100`). - **No journal entry at PO creation — `create_purchase_order()` never calls a poster.** A purchase order is a request, not yet an economic event: no goods have moved, no obligation exists. This is the deliberate opposite of `create_invoice()`, which posts immediately because *issuing* an invoice is itself the revenue-recognition event. Only `receive_purchase_order()` posts, matching the user's own framing that "received and billed" is one event here, not a separate three-way-match "enter the supplier's invoice" step nothing in this session's brief called for.
- **`purchase_orders.balance` tracks `received_value - amount_paid`, not `total - amount_paid`.** `total` is the full ordered amount — informational, "what this will cost if everything arrives" — and never itself an AP claim. `received_value` only grows as goods actually arrive, because a business only owes a supplier for what it's actually received; a partially received PO can already carry a real, payable AP balance while the un-received remainder owes nothing yet.
- **`receive_purchase_order()` reuses `adjust_product_stock()`'s own locked-read-then-write discipline** (lock the product row, then update it) rather than inventing a new stock-mutation path, per the user's explicit instruction — extended with `create_sale()`'s stable-id-order multi-row locking, since one receiving event can touch several PO lines/products at once and needs the same deadlock-avoidance guarantee. `stock_movements` finally gets a real, journaled use for its long-reserved `'Purchase'` movement type — previously only ever inserted directly by `inventory-store.ts`'s `addProduct()`/`addProducts()`, per Session 14's own "not posted" scope note, which this session doesn't touch (that path remains out of scope, a different, non-PO way stock can arrive).
- **A real bug caught before it ever reached the frontend, the same "verify the mechanism before verifying the screen" discipline Session 16 established**: the first draft of `receive_purchase_order()` inserted the `purchase_order_receipts` header with a placeholder `total_value` of `0`, then tried to `UPDATE` it once the receiving loop had computed the real total — but that table deliberately has no `UPDATE` grant at all (immutable the moment it's created, the same "once posted, permanent" rule `journal_entries`/`day_closes`/`bank_reconciliations` already established), so the RPC's own update failed with a bare `42501`. Fixed by splitting the function into a validate-and-total first pass (reads `purchase_order_lines`, checks quantities, sums the value — touches nothing yet) and a mutate second pass, so the header is inserted exactly once with its real total already known, never patched in afterward.
- **`purchase_orders`/`purchase_order_lines`' RLS deliberately does NOT take the Session-16 `bank_reconciliations_update`-style status-narrowed `USING` clause**, despite the user's explicit warning to watch for exactly that gap — considered and deliberately not applied here, for a real reason, not an oversight: a bank reconciliation's completion is a one-way, all-at-once freeze (`completed_at is null` flips to `false` as part of the very update that completes it, which is what tripped the missing-`WITH CHECK` bug), while a purchase order has an ongoing lifecycle even after reaching `'received'` — payments keep landing against it until `balance = 0`. There is no "this column's gating value flips from true to false as part of the very update being performed" situation here for a narrowed `USING` clause to trip over. Transition legality (can't place a non-draft PO, can't receive against a cancelled one, can't cancel one with any receipts) is enforced inside each RPC's own explicit checks instead, the same shape `create_sale_return()`/`complete_bank_reconciliation()` already use for their own precondition validation.
- **`purchase_order_receipts`/`purchase_order_receipt_lines` are immutable the moment they're created** — no update or delete policy at all, matching `journal_entries`. **No "reverse a receipt" mechanism exists** — a genuine receiving mistake needs a manual correcting stock adjustment plus a manual journal entry, the same real-world remedy an invoicing mistake needs today via `reverse_journal_entry()` plus a fresh, correct entry. Flagged directly as a scope boundary rather than built, since nothing in the session's brief asked for an undo path.
- **Deliberately out of scope, flagged rather than invented**: no VAT/discount modelling on purchase orders (every VAT rule in the spec is framed around what's charged to customers; Input VAT recoverable on purchases is a real, separate accounting concept this session was never asked to build) and no new "withdrawal" transaction type (the spec's "matching deposits and withdrawals" phrasing, quoted from Session 16's own brief, doesn't apply here — money already leaves/arrives `1010` via existing payment methods; a statement line just carries either sign).

**Cost price becomes nullable, and every consumer had to stop treating a missing one as zero.** `products.cost` was `not null default 0` since Session 1 — genuinely-unknown cost and confirmed-free cost were indistinguishable, which silently understated margin, valuation, and COGS for exactly the products a business is least sure about. `supabase/migrations/20260815100000_nullable_cost_price.sql` drops both the `not null` and the `default 0`; `Product.cost` (`data/inventory.ts`) is now `number | null`, with `hasCost()` (`data/inventory-store.ts`) — a type guard, not just a boolean check, so callers get `cost: number` narrowed automatically — as the one pattern every cost-derived calculation in the app now goes through instead of its own `?? 0`.
- **The ledger side was the real risk, not the type change.** Every COGS-computing poster function (`post_sale_journal_entry()`, `post_invoice_journal_entry()`, `post_sale_return_journal_entry()`, `post_stock_adjustment_journal_entry()`) already `coalesce(cost, 0)`'d defensively, for a column that was until now guaranteed non-null — flipping it nullable with no further change would have made every one of them silently understate COGS with zero error and zero audit trail the moment a line involved an unpriced product. COGS still has to post as an estimate (a sale can't be blocked from completing because a product's cost isn't filled in yet — that's a real usability regression nothing asked for, and a journal entry still has to balance per Session 13's deferred trigger), but `journal_entries` gains a new `cost_data_incomplete boolean not null default false` column, threaded through `_post_journal_entry_rows()` and set by each poster (via `bool_or(product.cost is null)` over the contributing lines) whenever any line's cost was estimated rather than confirmed. The affected journal line's own `description` also gets an inline "(estimated — cost price missing for one or more items)" suffix, so the estimate is visible reading the ledger directly, not just via the flag column. `accounting.journal-entries.tsx` renders an amber "Cost estimated — cost price missing" badge on any flagged entry, the same badge slot as "Reverses X"/"Reversed by Y".
- **Every report that derives from cost now distinguishes "confirmed cost" from "no idea," not just "zero cost."** `reports.ts`'s `costOf()` used to return a bare `number` (`match?.cost ?? 0`, collapsing "no product matched" and "matched but no cost" into the same silent zero); it now returns `{ cost: number; complete: boolean }`, and `TxnLine`/`MarginRow`/`ProductRow` all gained a `costIncomplete: boolean` that ORs up from line → product → category → the report-level `costDataIncomplete`/`incompleteCostProductCount`. **Connection resilience for flaky internet is added — three pieces, purely frontend, no migration.** Deliberately *not* offline editing: nothing is queued for later, and no transaction is ever accepted without a live server round trip — the goal is surviving a dropped connection gracefully, not weakening the atomic stock/pricing/authorization guarantees `create_sale()`/`create_invoice()` already provide.
- **A real, structural way to tell "the connection dropped" apart from "the server rejected this," not string-sniffing a message.** `frontend/src/lib/network-error.ts`'s `isNetworkError()` checks `error.code === ""` as the primary signal — confirmed by reading `@supabase/postgrest-js`'s own `PostgrestBuilder.then()`: its default (non-`throwOnError`) `.catch()` handler resolves a genuine fetch-level failure to an error object shaped like a real `PostgrestError` but with `code` left empty, while every real Postgres/PostgREST error always carries a real SQLSTATE-derived code (`"23505"`, `"P0001"`, `"42501"`, ...) — confirmed live with a real client pointed at an unreachable host, not just read from source. The message pattern (`/fetch|networkerror|.../i`) is required in addition, not instead — getting this wrong in the "network error" direction is the worse failure mode, since it would hide a real rejection behind a misleading "check your connection" message.
- **`frontend/src/data/connectivity-store.ts`'s `useOnlineStatus()`** is a `useSyncExternalStore` hook over the browser's own `online`/`offline` events (`navigator.onLine`), with the same fixed-`true`-during-SSR `getServerSnapshot` every other `*-store.ts` in this codebase already uses to avoid a hydration mismatch. `frontend/src/components/offline-banner.tsx` renders a persistent, unmissable top bar — deliberately not a toast, which auto-dismisses on its own timer regardless of whether the connection has actually returned — mounted once in `__root.tsx`, outside the `AppShell`/`AuthGate` split, so it shows on `/login` too. A brief "Back online" confirmation shows for 4s once the browser reports reconnection.
- **POS checkout (`pos.index.tsx`) and invoice creation (`invoice-form.tsx`) both already left the cart/form completely untouched on any failure** — `resetSale()`/navigating away only ever happens on the success path, so "keep the work exactly as it was" needed no new code, just correctly classifying the failure and giving it a distinct, stickier UI than the ordinary toast: a `connectionIssue` state renders an inline banner ("Connection lost — this sale/invoice wasn't submitted... your cart/form is untouched") with its own Retry button that just calls the same `checkout()`/`submit()` again — a real rejection (insufficient stock, an unpriced product, a declined discount) still only ever gets the ordinary toast, unchanged.
- **Retry here means a user clicking a button again against still-intact state, never an automatic background retry or a queued write** — matching the task's own explicit boundary. This is deliberately *not* full request idempotency: the overwhelming majority of a real "connection dropped" failure means the request never reached the server at all, so a manual re-submission is safe by construction; the narrow remaining case (the server received and committed the request, but the response was lost before the client saw it) has no idempotency-key protection here, since building one would be materially new backend infrastructure, not a resilience fix — flagged as a known, deliberate scope boundary rather than silently glossed over.
- **`invoice-form.tsx`'s two-step submit (create-or-update, then optionally log a payment) needed one real correctness guard beyond simple message classification**: a new `pendingInvoiceId` state is set the moment `createInvoice()`/`updateInvoice()` actually succeeds within an attempt, and a retry checks it first — skipping straight to retrying `addPayment()` alone if the invoice itself already exists, rather than calling `createInvoice()` a second time and minting a genuine duplicate invoice. `updateInvoice()` has no equivalent risk (a plain update-by-id is safe to repeat) but goes through the same guard for simplicity, since repeating it is harmless.
- **A real, pre-existing bug found and fixed as a necessary side effect, not scope creep**: `invoice-form.tsx`'s `submit()` used `catch (err) { setError(err instanceof Error ? err.message : "Could not save the invoice.") }` — the exact bug already found and fixed at six other call sites (`getErrorMessage()`'s own doc comment): supabase-js's default error objects are plain objects, not `Error` instances, so every real backend message here was silently replaced by the generic fallback. Building `isNetworkError()`'s classification meant this catch block had to actually inspect the real error shape first, which made the pre-existing bug impossible to leave in place while wiring the fix in — replaced with `getErrorMessage()`, matching every other mutator in this codebase.
- **Read-only caching for reference lookups is what `useInventory()`'s existing module-level cache already was — this only makes its age honest, never widens what it's trusted for.** `InventoryState` gains `lastSyncedAt: number | null` (epoch ms), set only on a *successful* `loadInventory()` — a failed background refresh (checked while genuinely offline) leaves it exactly as it was, which is what keeps a "Synced X ago" label honest rather than silently resetting the clock on a refresh that didn't actually happen. `reloadInventory()` is a new thin exported wrapper around the module's existing internal `reload()`, matching `invoice-store.ts`'s own `reloadInvoices()` precedent (a domain-named export, not a bare `reload` that could collide with another store's own). `frontend/src/components/sync-status.tsx`'s `SyncStatus` renders a small, self-ticking "Synced Xs/Xm/Xh ago" label with a manual refresh action, added to the Inventory list and the product detail page — the two places CLAUDE.md's own examples name ("checking a price or stock count") — and deliberately **not** to POS or invoicing, since those are exactly "anything that gates a decision with real consequences": `create_sale()`/`create_invoice()` already re-check stock/price/cost live, server-side, on every call regardless of what this cache shows on screen, and this session made no change to that boundary at all.

**Cash overpayment at POS was completely broken and is now fixed — backend only.** `supabase/migrations/20260831110000_fix_cash_overpayment_posting.sql`. `create_sale()` deliberately lets cash exceed the total (its validation only rejects underpayment and *non-cash* overpayment) and stores the full tender in `sale_payments.amount`, but `post_sale_journal_entry()` debited that full tender while the credit side is anchored to `sale.total` — so any sale with change due produced an unbalanced auto-posted entry, `_post_journal_entry_rows()`'s balance pre-check raised, and the whole `create_sale()` transaction rolled back. Confirmed live: a GHS 184 sale with GHS 200 cash tendered → `"debits 316.00 do not equal credits 300.00"`, no sale created. Broken since Session 14 (Auto-Posting) — every session's verification used exact payments, so the overpay path was never exercised. No historical data to migrate: overpay sales never got created.

**Voiding a mistaken POS sale / invoice is added — an erasure, not a return.** `supabase/migrations/20260901110000_void_sale_and_invoice.sql` adds `void_sale(p_sale_id, p_reason)` and `void_invoice(p_invoice_id, p_reason)`; `pos-store.ts`/`invoice-store.ts` expose `voidSale()`/`voidInvoice()`; a shared `components/void-transaction-dialog.tsx` (reason mandatory, Manager-only) is wired into the invoice detail page and the POS Sales-history drill-down.
- **A void is deliberately not a return.** A return is a real customer interaction (goods come back, money or credit moves, the sale still happened); a void says the whole transaction was rung up by mistake and should never have existed. So a void reverses **every** journal entry the transaction produced, restores every unit of stock a POS sale moved, and marks the row dead — it creates no `sale_returns`/refund record.
- **Ledger reversal reuses `reverse_journal_entry()` exactly** — one call per journal entry the transaction produced. A POS sale has exactly one (`source=('sales', id)`); an invoice has its creation entry (`('invoices', id)`) **plus one per payment** (`('invoice_payments', pid)` — real cash/bank, WHT-credit and Deposit legs alike), each reversed. No reversal lines are hand-built. Each reversal is dated `current_date` (a correction happens today, never backdated). Verified: original + reversal net to exactly 0 across every account, for both a sale and a paid invoice.
- **Invoices never deduct stock** (see `create_invoice()` — "Invoices never touch stock"), so `void_invoice()` only reverses the ledger and sets `balance = 0`; only `void_sale()` writes stock movements, using a **new `'Void'` `stock_movements` type** (added to the CHECK), distinct from `'Return'` so a voided-sale reversal is never mistaken for a customer return in stock history.
- **Four hard blocks, each a clear message, no exceptions:** (1) the transaction's day is closed/reconciled — for a sale `sold_at::date`; for an invoice its issue date **or any date it took a payment**; (2) it already has returns/exchanges against it (structurally POS-only — invoices have no returns mechanism); (3) it is older than 7 days from the transaction date (`current_date - date > 7`); (4) not a Manager. Plus a fifth integrity guard: a sale/invoice that **fulfilled a customer deposit** can't be voided (that would strand the deposit as Fulfilled against a dead document). Empty reason and re-voting an already-voided row are also rejected.
- **The void columns are writable only from inside the SECURITY DEFINER RPCs.** A `reject_direct_void_write` `BEFORE UPDATE` trigger on both tables rejects any change to `voided_at`/`voided_by`/`void_reason` when `current_user` is one of the PostgREST/Supabase app roles (`authenticated`/`anon`/`authenticator`/`service_role`) — inside the SECURITY DEFINER function `current_user` is the owner, so it passes; a direct REST PATCH is rejected. The trigger also makes a void one-way (can't clear `voided_at`) and freezes a voided invoice against every other write path (`update_invoice()`, `record_invoice_payment()`'s balance update). Two more `BEFORE INSERT` guard triggers (`sale_returns`, `invoice_payments`) reject a return/payment against a voided parent. **`sales`' UPDATE grant is deliberately NOT revoked** — `create_sale_return[_batch]()` take a `SELECT ... FOR UPDATE` row lock on the sale, which Postgres requires the UPDATE privilege for; the trigger is the sole enforcement (verified: a direct authenticated PATCH of `sales.voided_at` is rejected by the trigger, not a missing grant).
- **The void is logged to `audit_log` via an `AFTER UPDATE OF voided_at` trigger** (new actions `'sale_voided'` / `'invoice_voided'` on the CHECK) — never a client insert, per Session 8's rule, and `audit_log` has no insert grant anyway. Actor is `coalesce(auth.uid(), new.voided_by)`.

The **ledger-derived** financial reports self-correct via the reversal entries, no change. Voided rows still appear in their list (so a Manager can find one) with a "Voided" badge + a who/when/why banner.

**A same-day follow-up extended void to expenses** (`supabase/migrations/20260905090000_void_expense.sql`), reusing the sale/invoice mechanism exactly rather than inventing a parallel one — `void_expense()` is Manager-only (matching `create_expense()`'s own bar: Attendant has zero access to Expenses at all, Accountant/Auditor is read-only everywhere, so this loosens nothing), reverses the expense's one `('expenses', id)`-keyed journal entry via the same `reverse_journal_entry()`, and is blocked by the same closed-day and 7-day checks as sales/invoices — no fifth integrity guard was needed, since nothing in the schema references an expense row by FK and there's no returns-like or deposit-fulfilment-like concept for expenses to strand.
- **The structural trigger is reused verbatim, not redefined** — `reject_direct_void_write('expense')` is just a third `create trigger` call against the same `reject_direct_void_write()` function `void_sale_and_invoice.sql` already defines. Unlike `sales` (whose UPDATE grant had to stay for `create_sale_return()`'s row lock), nothing anywhere ever legitimately `UPDATE`s an `expenses` row — `create_expense()` is a plain insert-only entry point with no `update_expense()` counterpart at all — so `expenses` took the stronger of the two options and had its UPDATE grant revoked from `anon`/`authenticated` outright. Verified both layers independently, not just the revoke: a direct PATCH as `authenticated` fails at the grant layer (`42501`, revoke working); a direct PATCH as `service_role` (which still holds the UPDATE grant, matching the standard convention) is separately rejected by the trigger itself ("Void status can only be changed through void_expense()") — proving the trigger is real structural enforcement, not an artifact of the revoke.
- **`compute_day_totals()`'s `cash_expenses` sub-query gained `and voided_at is null`** (recreated verbatim otherwise) — the same "a same-day void nets correctly against the drawer, a closed day can't be affected at all because voiding one is blocked outright" reasoning already established for sales/invoices. `data/dashboard.ts`'s this-month/last-month expense KPIs and `data/reports.ts`'s `expensesInRange`/`previousExpenses` (which the whole Expenses report page derives from) both gained the matching `!voidedAt` filter; the Expenses list/detail pages show a "Voided" badge and banner (reusing the same shared `VoidTransactionDialog`, widened from `"sale" | "invoice"` to also accept `"expense"`) while excluding voided rows from every summary figure and the table footer total, the identical `liveRows`-style pattern the POS history and invoice list pages already use.
- **Verified end-to-end.** RPC: a fresh Cash expense voided within the window → reversal entry balanced and netting to 0 across every account, `audit_log` `expense_voided` attributed to the Manager. All blocks confirmed individually: non-Manager (Attendant) rejected ("Only a Manager can void an expense"), Accountant/Auditor rejected via `require_writable_role()`'s own read-only message, empty reason, re-void, 7-day (a crafted 10-day-old expense: "EXP-OLD001 is 10 days old"), and closed-day (open + close today, then reject voiding today's expense: "has been closed and reconciled"). In a **real browser** (dev-manager): voided a real freshly-recorded GHS 315.50 expense from its detail page — Void button visible, banner appears with the typed reason, button disappears, "Cash impact" field updates to "Voided — no longer affects cash on hand" — and the list shows the same expense with a "Voided" badge, excluded from the "Total expenses" card; the 7-day block surfaced as a clear in-dialog error on a real 126-day-old seeded expense ("EXP-1025 is 126 days old"); signed in as dev-auditor, the expense list still renders (read-only, as expected) with no Void button anywhere. `tsc` / `eslint` / `prettier` / `vite build` / `check-duplicate-function-overloads.sh` all clean; local DB reset afterward.

The Supabase client (`frontend/src/lib/supabase.ts`) supplies a `ws`-backed realtime transport only when `import.meta.env.SSR && typeof WebSocket === "undefined"` (Node < 22 has no native `WebSocket`, and `supabase-js` constructs a realtime client eagerly even when nothing subscribes to a channel) — keep that guard if touching this file, or SSR breaks on this Node version. `frontend/src/lib/database.types.ts` is generated via `npx supabase gen types typescript --local`; regenerate it after schema changes rather than hand-editing.

When wiring up a not-yet-migrated module, follow the Inventory/Customers/Sales/Expenses precedent: keep the `useX()` hook shape and mutator function signatures stable for unrelated consumers (delegate from a combined store into focused ones if needed, the way `sales-store.ts` now delegates to both `customer-store.ts` and `invoice-store.ts`), write the migration + `seed.sql` mirroring the existing dummy data, and grant `anon`/`authenticated`/`service_role` explicit table privileges (`supabase/config.toml`'s `api.auto_expose_new_tables` is off, so new tables 403 via the Data API without it; Postgres itself grants a brand new table nothing beyond the owner by default, whatever role creates it). RLS is on as of Session 7 (Auth & Roles) — enable it on any new table and match the locked 3-tier model from business-app-spec.md section 6 (Manager: full read/write/delete; Accountant/Auditor: read-only, no exceptions; Attendant: read/write only if the module is actually in their spec-granted list, no delete ever) rather than the shallower "any active staff, only Manager/Accountant-Auditor deletes" shape Session 7 originally used — that placeholder was superseded by the role-permissions-rewrite migration described above. Any function that inserts a new record should follow `create_invoice()`/`create_expense()`'s discipline: no client-supplied id, a plain `insert` (never `on conflict do update`), so a create can never silently overwrite an existing row — reserve a separate, explicitly-named `update_x()` for edits if the module needs them, requiring the row to already exist and failing loudly if it doesn't.

**Every new table/sequence needs all three roles' privileges decided explicitly, in the same migration that creates it — don't let this get rediscovered session by session the way it already has twice.** `anon` and `authenticated` are a case-by-case call tied to that table's RLS design (see above); `service_role` is not a judgement call — it always gets full `select, insert, update, delete` (plus `usage` on any new sequence), unconditionally, every time, because it already bypasses RLS by role attribute and is never exposed client-side, so there's no scenario where holding back its grant buys any real security. **`audit_log` (Session 8) is the one deliberate exception** — see the Data layer entry below for why an append-only-via-trigger table's security property lives at the `GRANT` layer, not the RLS layer, so `service_role` gets withheld there too. Don't treat that as a second precedent without the same "nothing should ever write here except its own triggers" property actually applying.

**Changing an existing function's argument list always needs an explicit `drop function if exists public.foo(<old signature>)` in the same migration, never just `create or replace function` with the new one.** Postgres treats a changed parameter list as a brand new overload, not a replacement — the old version stays defined and callable, silently, alongside the new one. This has already happened three times for real (`create_sale_return()`, `create_invoice()`, `_post_journal_entry_rows()` — the last one shipped broken to production and wasn't caught until live verification), which is why `scripts/check-duplicate-function-overloads.sh` exists; run it alongside `tsc`/lint/`db reset` before committing anything that touches `supabase/migrations/`.

## 🔐 Bootstrapping the first production Manager

Since Session 20 (Invite-Only Staff Onboarding), the public signup form no longer exists and `/auth/v1/signup` is disabled at the GoTrue level — the **only** way a staff login is ever created is an invite (`supabase.auth.admin.inviteUserByEmail()`), sent either from Settings > Staff (requires an existing, active Manager) or from this script. On a brand new hosted project, nobody exists yet to send that first invite from the app — that's what `scripts/bootstrap-production-manager.sh` is for, run once, by hand, by whoever holds the real project's `service_role` key:

```sh
SUPABASE_URL="https://<your-project-ref>.supabase.co" \
SUPABASE_SERVICE_ROLE_KEY="<the real project's service_role key, from Project Settings > API>" \
MANAGER_EMAIL="owner@realbusiness.com" \
MANAGER_NAME="Real Owner Name" \
./scripts/bootstrap-production-manager.sh
```

It sends a real invite (role `Manager`, same mechanism as an ordinary in-app invite) and then flips `protected = true` on the resulting `staff` row — after which `staff_protect_row` (Session 20 migration) makes that row's role, active status, and protected flag itself unconditionally unchangeable, and the row undeletable, for every role including Manager, at the trigger level, not just RLS. There is no path back from this short of a manual migration; only ever run it for the one real person who should hold that account.

Requires:
- The target project's real `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` — never hardcode these into the script or commit them anywhere, export them in your own shell first.
- The hosted project's own Dashboard signup toggle already flipped off (Authentication > Sign In / Providers > "Allow new users to sign up") — `config.toml`'s `enable_signup = false` only controls local dev.
- Typing `BOOTSTRAP` at the confirmation prompt — the script does nothing without it.

The script refuses to run against a `127.0.0.1`/`localhost` `SUPABASE_URL` (the exact inverse of `seed-local-dev-staff.sh`'s own safety check) — local dev has no need for a protected account and already has its own seed mechanism. **Never run this script for the user** — bootstrapping the real first Manager is explicitly their own step, with their own credentials, against their own project.

## Business Domain Rules

**Current phase:** Phase 1.5, wiring the frontend's existing dummy data to a real Supabase backend, plus adding real auth, roles, and audit logging. Do not build or scaffold Accounting core, Payroll, the real branch switcher, or Purchasing, those are Phase 2/3 and out of bounds until their phase comes up. If asked to build any of these ahead of schedule, ask first rather than building it.

"The real branch switcher is out of bounds" means the *feature* — UI to select among multiple branches, multi-branch business logic. It does not mean the one seeded branch's name is allowed to be a hardcoded string: `useCurrentBranch()` (`frontend/src/data/branch-store.ts`) reads it from the real `branches` row so a rename there is reflected everywhere, with no switcher and no dropdown. Don't reintroduce a literal "Accra Main Branch" (or any other hardcoded branch name) anywhere in the app — use the hook.

**branch_id everywhere.** Every table representing a real business record (products, stock movements, customers, invoices, POS sales, expenses) needs a branch reference from day one, even though the app only shows one branch right now. `Product` already has a `branch` field, replicate that on every table that doesn't have it yet.

**Cost price and selling price are always separate fields**, never merged into one "price". `Product` already does this correctly (`cost`, `price`), keep that split in every table and every calculation that touches margin.

**VAT and discounts:**
- VAT defaults to 20%, but must be a configurable setting, never hardcoded
- VAT can toggle per line item or for a whole sale
- Discounts (percentage or fixed) apply per item or to a whole sale, at manager discretion, with no cap
- Every discount and VAT override must be logged with who applied it, this is what the audit log is for

**Naming discipline.** "Gross profit" (revenue minus cost of goods sold) and "operating margin" (gross profit minus recorded expenses) are never renamed to just "profit" or "net profit" anywhere in the UI, copy, or code comments. Neither figure accounts for payroll, which doesn't exist yet.

**Full spec:** `/docs/business-app-spec.md` has the complete phase breakdown, module detail, and business rules. Check it before making a scope or schema call this file doesn't cover. (Copy it into the repo now if it isn't there yet, it currently only exists as a file Eyram has locally.)
